# Phase 10 Architecture Review

## Overview

Phase 10 adds the Reports page as a self-contained feature under `apps/web/src/features/reports/`. It follows the established feature-folder pattern (types, mock provider, hook, presentational components, token-based CSS) and introduces no changes to the platform foundation.

## Layering

```
ReportsPage (composition / route target)
 ├── useReports                    (mock data + filter state + drill-down state)
 ├── components/ReportsToolbar     (search + category/status/owner/frequency/date filters)
 ├── components/ReportsSummary     (5 MetricCards + records/filter summary row)
 ├── components/ReportsGrid × 2    (Recent Reports / Scheduled Reports)
 ├──   └── ReportCard              (per-report card)
 ├── components/ReportHistoryPanel (global Execution History, tone-coded runs)
 ├── components/ReportTable        (Report Library, row click → detail)
 ├── components/ReportPreviewPanel (preview tables of a report)
 └── components/ReportDetailPanel  (drill-down view, replaces page body)
     ├── ReportSchedulePanel       (schedule metadata + recipient chips)
     ├── ReportHistoryPanel        (per-report run history, reused)
     └── ReportPreviewPanel        (per-report preview, reused)
reports.types.ts   (shared types)
reports.mock.ts    (deterministic mock source)
reports.css        (feature-scoped, token-based styles)
```

## Data Flow

1. `useReports` memoizes `getMockReports()` once. Reports flow into a memoized filter pipeline: `matchesFilters` checks search + exact category/status/owner/frequency matches and last-run date bounds; `deriveOptions` builds select options from the report set.
2. KPIs and the 45 execution-history entries are derived once from the reports in the mock and flow as props to presentational components.
3. Derived views (`recentReports` = top 3 by last run, `scheduledReports` = Scheduled-status reports, `previewReport` = first filtered report) are memoized in the hook.
4. Drill-down is local UI state: `openDetail(report)` sets `selected`; the page renders `ReportDetailPanel` instead of the list view; `closeDetail` returns. Per-report history entries are mapped from `report.history` with `reportId`/`reportTitle` filled in.

## Component Principles

- **Container/presentational split**: only `ReportsPage` and `useReports` hold state/composition; every child is props-driven and re-usable.
- **Single responsibility**: 9 components, each rendering one dashboard region. `ReportsGrid`, `ReportHistoryPanel`, and `ReportPreviewPanel` are generic and reused across list and detail views.
- **Stable keys**: KPIs, reports, history entries, preview rows/columns all keyed by id.
- **Tone system**: status tones map onto the design-system Badge/MetricCard tone contracts; run statuses map Success=success, Failed=danger, Running=info.

## State Management

- `useState` only: the filter object and the selected report for drill-down. No global store, context, or URL sync. Filtering is computed on every render via memoized `filteredReports`.

## Styling

- `reports.css` uses only design tokens; dark theme inherited automatically via token swaps.
- Class prefix `reports__` / `reports-detail__` prevents collisions with other features.
- Breakpoints: ≤1180px collapses toolbar fields, KPI row, card grid, and detail grids to 2 columns; ≤720px goes fully single-column with stacked headers.

## Routing

- Wired through the existing `getRouteElement` switch in `router.tsx` — the same pattern used for Phases 1–9. `routes.ts` already contained the `/reports` family entries; no config change was needed.
- `/reports` previously fell through to `PlaceholderPage`; it now renders `ReportsPage`.

## Mock Strategy

- The mock module is the single contact point for fake data. 9 reports are defined declaratively via a `defineReport` helper; preview tables are generated deterministically by a `buildPreviewTable`/`cellValue` pair (dates, weeks, products, machines, percentages, scores); history is generated by `buildHistory` with a fixed Success/Success/Success/Failed/Success cadence. KPIs are computed from that data and labeled Mock Data in the UI. Replacing with an API later only requires changing `getMockReports` (or the hook), leaving components intact.

## Dependencies Added

- None. Phase 10 consumes only existing design-system primitives (`Badge`, `Card`, `MetricCard`, `EmptyState`, `ChartContainer`) and `react` hooks.
